# Connection reuse and durable scan windows — 0.11.2

Date: 27 October 2026 (America/New_York). Android version 0.11.2-sync-preview, code 19; Rust workspace 0.11.2.

## What changes for the user

Install over the existing Independent Sync Preview, unlock the same wallet and explicitly reconnect. The saved node, route, wallet keys and scan start remain in place. A scan resumes at its last durable checkpoint; no rescan or wallet recreation is required. The recent-block choice and detailed private notification counters from 0.11.1 remain available.

This update reduces connection setup, repeated tip checks and encrypted scan-cache writes. It keeps local scanning and the existing Rust protocol adapters. It does not introduce a remote scanning service or send private keys to a server.

## Reuse the selected connection

Previously each RPC created a socket, performed HTTPS authentication when applicable, sent `Connection: close` and discarded the connection. The transport now pools at most one HTTP/1.1 connection for its immutable node/route session. Clones share that pool and serialize requests. The selected URL supplies the original HTTP authority and TLS hostname. Direct system DNS/Android-resolved addresses and Tor remote DNS keep their existing boundaries.

A response must pass status, encoding and size checks and be read completely before its connection returns to the pool. Connections used within the preceding 20 seconds are eligible for reuse if Hyper reports them ready. Older or known-closed connections are discarded before the next request. This is a checkout rule, not a promise that an idle socket closes at exactly 20 seconds. Server-requested closure, cancellation and transport/session destruction also discard it. Cancellation closes an idle socket without waiting for the engine or pool mutex.

An interrupted, malformed, oversized or failed response discards its checked-out socket. Once an application request has been attempted, an error is returned without automatic retransmission. A lost broadcast reply therefore cannot trigger an automatic second broadcast. A connection that closes during an in-flight read may still require the normal explicit retry/reconnect flow. Existing durable pending-payment retry sends the same signed bytes.

The 32 MiB maximum response, 90-second request timeout, identity encoding, route allowlist, certificate/hostname checks and cancellation remain. No redirect, automatic protocol downgrade, alternate node, alternate resolver or Direct fallback is added.

## Group quiet reads, publish durable progress

The existing adaptive read size remains 32–512 blocks, starting at 128, with reduction when a response exceeds its existing cap. A scan call now groups those bounded reads into a window of at most 2,000 blocks. It checks the tip/reorg anchor once, clones state once and reuses one scanner within that window. After a read, the window ends if it has taken about two seconds or detected a new receipt, local spend or outbound confirmation. A slow individual RPC can exceed the time target; it is not a two-second hard timeout.

The engine saves the completed window through the existing encrypted atomic store before returning its status. UI/notification progress therefore describes committed work, rather than a volatile count. Failure, cancellation or process death can repeat unreported blocks since the last checkpoint. It cannot invalidate an already returned checkpoint. Pause lets the current bounded call finish; explicit lock cancels it. There is no dirty state retained across scan calls and no new shutdown flush that could delay locking.

All block numbers/linkage, transaction/output-index checks, local scan/key-image handling, genesis checks and reorg/reservation behavior remain. Receipts/spends/confirmations end grouping after their current bounded read; they do not wait for another quiet-history window. Other state mutations still save immediately. In particular, the signed transaction and input reservation commit before broadcast, exactly as before.

## Measured overhead

The final isolated test used Monero CLI 0.18.5.4, an offline synthetic chain and the same 1,000 blocks/scanner. Its loopback adapter injected 25 ms before each RPC; connection setup was excluded from this scan comparison.

| Scan mode | RPCs | Durable saves | Elapsed |
| --- | ---: | ---: | ---: |
| Fixed 32-block windows | 96 | 32 | 3.375 s |
| Adaptive reads, one checkpoint per read | 12 | 4 | 0.838 s |
| Adaptive reads, coalesced windows | 6 | 1 | 0.622 s |

A separate 20-RPC HTTP test injected 25 ms per new TCP connection: closure after each response used 20 connections / 0.543 s; reuse used one connection / 0.032 s. Both completed the same 20 requests. Assertions check request/connection counts and correctness, not elapsed-time ordering under host load.

These measurements isolate overhead. They do not establish public-node, phone, historical-chain or Monero One speed parity. Real performance depends on node latency/bandwidth, block contents, local scanning and storage. This update applies the reviewed ideas of amortized cache saves and less frequent progress publication to this engine; it does not port iOS location-based background execution or treat an iOS startup-priority improvement as a raw scan benchmark. Android retains its existing explicit, bounded foreground-service policy.

## Regression coverage

Tests cover shared pooled use, server closure, partial-body interruption, idle cancellation and a lost broadcast reply without automatic replay. The real-node test covers interrupted scan windows retaining the last reported checkpoint across encrypted reopen, an activity-triggered early save, scan equivalence, recent-height initialization, response-size reduction and the complete signed-payment/lost-reply/reservation/reopen/exact-byte-retry/confirmation/reorg path. Test fault injection and save counters compile only under `cfg(test)`.

See [VALIDATION.md](VALIDATION.md) for build, signature, artifact and execution results. No physical-device throughput, notification rendering, Android instrumentation execution, live Tor or hardware-wallet execution was performed for this release.
