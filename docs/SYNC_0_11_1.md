# Sync start, request overhead and notification progress — 0.11.1

Date: 27 October 2026 (America/New_York). Android version 0.11.1-sync-preview, code 18; Rust workspace 0.11.1.

## Why a brand-new wallet was slow

Both generation adapters deliberately stored restore height 0. Connecting immediately scanned from genesis even for keys just created on this phone. The earlier rescan implementation used the minimum of the entered height and the saved start, so it could not correct that choice by moving forward. Initializing a nonzero scan also requested every cumulative RingCT-output count before the start, although only the last count was needed. Each scan batch contained only 32 blocks, followed by repeated tip/linkage checks and an encrypted atomic save.

The notification displayed an integer percentage only. Early progress through a large range therefore remained 0% even while blocks advanced. It did not include current/target or remaining-block counters.

## Choosing the range

An explicitly connected wallet with no scanned checkpoint and start height 0 now waits at **Choose scan start**. **Scan from beginning** retains the full-history option. Generation/import and saving/selecting a node remain offline; no node, route or protocol changes automatically.

For a wallet created today:

1. Install this APK as an update and unlock the same wallet.
2. Connect to the already selected node. If a scan is running, tap **Pause to change scan start** and let its current batch finish.
3. Tap **Change scan start → Wallet created today · use recent blocks**.
4. Review the start block and confirm that it is before the wallet's first payment, then tap **Apply and sync**.
5. Enable **Allow background sync** and notifications to see progress while leaving the app. The wallet UI still locks; returning requires device credentials.

The shortcut proposes the currently connected node's height minus 1,440 blocks, bounded at 0. This is a buffer for the explicit new-wallet choice, not proof of a wallet birthday, independently verified chain height or old payment coverage. A restored/older wallet needs an earlier known height or 0. Changing the field clears the confirmation; a forward start requires checking it again, and cannot exceed the currently reported tip or the existing UInt height bound. No phone-clock estimate silently skips history.

The native engine permits a forward start only when its local outputs, history and payment journal are all empty. It rejects a forward change when any of these records exist. Earlier rescans remain possible; the complete outbound journal/input reservations and configured subaddress count survive them. A successful range change clears old scan results, saves the chosen start through the existing encrypted AtomicFile-equivalent native store, resets completion and scans the new range. The encrypted key vault, seed derivation, addresses and node settings are unchanged. Reopen and Direct/Tor changes retain the saved start.

A pause stops foreground polling, waits for the active bounded batch to commit and leaves the connected engine available for an explicit range change or resume. It stops the background service/wake lock once idle. Explicit lock, route/node changes and background policy still revoke the live session; pause does not grant background or signing authority.

## Throughput changes

- Start at 128 blocks per batch. Grow toward 512 when a batch takes under 1 second; shrink toward 32 when it takes over 4 seconds. Do not invent progress while a batch is in flight.
- Retain the upstream bounded binary block-fetch adapter, all number/linkage, transaction, output-index and local scan checks, and encrypted atomic commits.
- If a larger read exceeds the unchanged response cap, halve the block count to a minimum of 32 and retry only that read against the same consented node/route. Keep this smaller ceiling for the session. Do not retry sends, disable TLS, change nodes, bypass validation or increase the response bound.
- Initialize a nonzero start with only the cumulative count at the preceding block, using the existing upstream distribution API. Reconcile the absolute index against the fetched blocks as before. Avoid downloading millions of unneeded historical counts.

The isolated synthetic-chain benchmark scans the same 1,000 blocks with the same scanner and validation. A 25 ms delay is injected before each loopback RPC request. Forcing the prior 32-block size used 96 requests and 3.5875 seconds; adaptive batches used 12 requests and 0.9784 seconds in the first completed run. Handshake requests are excluded from both counts. This demonstrates amortized request overhead under those conditions; it is not a public-node, Android, full-history or Monero One comparison. Exact phone speed and cross-wallet parity are unmeasured.

Monero One's own documentation says scanning runs locally and depends on wallet age/node speed; its Android app wraps wallet2 through monero-kit-android. This update retains this project's Rust engine and does not replace its cryptography or upload keys to a light-wallet service. Sources: [Monero One FAQ](https://monero.one/faq), [Android source](https://github.com/bwgh0/MoneroOne.Android), [Monero restore-height guide](https://www.getmonero.org/resources/user-guides/change-restore-height.html).

## Visible notification progress

The private foreground notification now shows the real fractional percentage and **Block X of Y**, with remaining blocks and the saved start height in expanded text. Very small positive progress reads **<0.01%** rather than appearing stuck at 0%. The progress bar uses 10,000 units. The same percent formatter is used on the wallet card and its accessibility description. Only verified native completion can display 100%; unknown, disconnected, paused, error and tip-check states cannot do so.

No balance, address, node URL, key or transaction data is included in notification content. Lock-screen secrecy and **Stop and lock** remain. Background sync/notification permission remain explicit session choices. Idle start-selection/paused states terminate the service instead of retaining an idle wake lock. Android may hide private content on the lock screen according to the user's settings.
