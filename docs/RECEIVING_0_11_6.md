# Receiving addresses — 0.11.6

Preview 2 code 24 supports the primary address and up to 1,000 deterministic account-0 subaddresses. Open Receive, choose New subaddress, optionally enter a label and create it. The new address is selected after its index/label have been saved encrypted. Choose receiving address switches to an existing address; Save label renames it. QR and Copy address always refer to the selected address. Creation, selection and labels work offline after the completed saved wallet is unlocked. They do not contact a node or enable network access.

Address indices, local labels and the selection are additive fields in the existing authenticated encrypted scan state. Old caches default to subaddress 1. Already-received outputs also reconstruct their highest used index on opening an old cache, and rescans retain all address metadata and outbound reservations. Indices are never deleted/reused as an address-book cleanup operation. Creation is bounded at 1,000; labels are bounded to 64 Unicode code points/256 UTF-8 bytes and reject controls and directional-override/isolate characters. Neither labels nor addresses are included in network logs or notifications.

Every scan watches the primary address and all 1,000 subaddresses this app can expose. The maintained upstream scanner registers that deterministic range once per active engine and reuses it between scan windows. A seed restore can therefore find payments throughout this supported range even if local labels/count were lost, provided the restore height precedes the receipts. Discovery extends the visible used-address range. Labels and the unused-address list are local metadata, not encoded in the seed; unused addresses can be recreated deterministically. Existing cached history that was originally scanned with only 20 addresses may need an explicit earlier rescan to discover an older payment to a higher address. No historical range is silently skipped or moved forward. Other accounts and indices beyond 1,000 remain outside this preview's scan scope.

The address book shares the active engine/cache lease when connected, so address edits cannot race a scan, payment reservation or another writer. Offline calls reserve a cancellable local child owned by the unlocked wallet. They construct no endpoint, runtime, daemon, sockets or Tor client. Cache I/O and engine locking never hold the owner's key mutex; locking the wallet can cancel local work. Kotlin adopts a result only for the same live owner/epoch and unlocked stage. Address changes and payment quote/auth actions cannot start over one another; returning through device unlock remains available during an outstanding local operation; background timers pause while the address operation is outstanding. An already requested atomic metadata save may finish during cancellation, but another address operation is never initiated by a background service.

The receive screen binds each QR bitmap to the exact address used to generate it, hides an old bitmap immediately when the selected address differs and generates the replacement off the UI thread. The list of up to 1,001 entries uses a bounded lazy list and derives only the selected full address for display.

Hardware and generic view-only wallets can derive receiving addresses using their existing viewing authority; they do not gain a spending key, local payment signing or verified spent-status coverage. Network, node, route, wallet slot, backup and clipboard policies remain unchanged.
