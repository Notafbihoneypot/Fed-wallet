# Project rules

- This is an independent Android wallet. Keep the interface original and native, with Kotlin/Compose and a Rust application core.
- Reuse maintained Monero protocol machinery through a narrow adapter. Do not invent cryptography or silently replace seed derivations.
- Never ship a default node list, automatic node selection or silent failover. The user authorized up to five named user-added endpoints, explicit selection/edit/removal and encrypted migration of existing entries; removing an active node must leave no automatic replacement. Offline setup must not construct a networked daemon client.
- The user authorized remembered network/background preferences after setup. Enabling network access remembers consent for that exact saved wallet, node and route; reconnect only after authenticated unlock. Saving/changing a node alone never connects and revokes remembered network consent. Turning network access off or Stop and lock revokes it; normal UI locking disconnects but preserves the preference for the next unlock. Automatic updates pause during payment entry/review/authentication. An already device-authorized immutable signed transaction may finish publication in a consented background session; never prepare, re-quote or sign another transaction there. Routine updates are batched. Background continuation requires explicit consent and a live bounded dataSync foreground service; keep its UI locked, poll after catch-up, stop on error/timeout, and never reopen keys after process death. Preserve the other encrypted endpoint when switching direct/Tor slots; an empty slot never falls back. Keep cloud-backup UI absent and platform backups disabled.
- Sync animation is decorative: percentages, heights and completion come from live native state. Unknown progress stays indeterminate; cached/error/disconnected state must not show verified completion. Post-sync Tor selection opens settings and keeps networking off until explicit consent.
- Keep the route explicit at the Rust boundary. Direct accepts normal HTTP/HTTPS nodes and may use system DNS; Tor accepts v3 onion/HTTPS endpoints, resolves destinations through Arti and must never fall back to direct. Changing the node or route revokes the old session and requires explicit network consent. Show the route and direct-IP/HTTP privacy cost before connecting. A readiness flag is not proof of routing.
- Never elevate node trust to bypass key-image import restrictions. Keep key-image mapping and spent detection local.
- View-only and hardware modes must not gain local signing authority. Make incomplete spent-status coverage visible.
- Mainnet software wallets are authorized by the user's explicit request to fix the preview's mainnet restriction. Keep mainnet/stagenet identities, recipient validation, genesis checks and encrypted scan state separate. Preserve existing test wallets and require an explicit authenticated action to create a separate mainnet copy. View-only and Keystone wallets must remain unable to sign.
- Verify actual signed transaction bytes, cryptographic validity and payment intent before broadcast. A caller-supplied summary alone is insufficient.
- Never log or upload seed phrases, spending keys, view keys, full transactions or node credentials.
- Keep unsupported wallet operations visibly unavailable. Do not create fake balances or market this foundation as money-capable.
- Save created setup drafts encrypted before displaying keys; pausing/backgrounding must keep durable progress and preserve unfinished backup verification. Never store plaintext setup in preferences or saved state.
- Keep both Resume setup and explicit Discard setup. Discard requires a separate confirmation and device authentication, targets the exact unfinished draft and must never delete a completed wallet, node settings or copied clipboard text.
- A user-copied seed remains on the clipboard until explicit Clear copy/replacement or OS behavior. Do not add exit, lock, page-close or timer clipboard clearing.
- Run scripts/check.sh for Rust changes. Regenerate Kotlin bindings after FFI changes and compile the Android source. Record device and hardware tests separately from host compilation. Background scans may retain the active native wallet in memory only with visible opt-in, bounded wake lock, a Stop and lock notification, no signing/auth action and no restart after process death.
- Preview 2 uses app.independentwallet.android.syncpreview2 and its backed-up RSA-4096 signing identity, certificate SHA256 01afd9a36efbb0d6573d8f12764164a14af3d99faa4a97ccfce45dff82cd52b5. The user explicitly requested a new installer after original-key loss. Never regenerate or silently replace this identity. Keep encrypted APK-signing key/password backups separate from public source/APKs/reports, preserve the old app/data, and do not claim automatic wallet/node/pending-journal transfer. PREVIEW2_SIGNING.md records recovery and signing limits.
- Receiving addresses support account 0, primary plus at most 1,000 subaddresses. Scan the entire creatable range, persist indices/labels/selection encrypted before exposure, preserve them on rescan, and never silently reuse/delete issued indices. Seed restore does not restore local labels/unused issuance history. Keep view-only/hardware authority unchanged. Local cache work must remain owner-cancelled and single-writer with no network construction or owner mutex held across I/O. QR frames must match the current selected address; do not display a stale QR beside new text. The delivered installer must disable Java/native debugging. Keep the remaining upstream advisory alerts visible in validation/security notes until actually resolved.

- Public decoy-count history may be cached encrypted separately from the funds/payment journal, with bounded pages and a hard count cap. Scope it to the exact wallet namespace, normalized selected node and explicit route; check its chain hash before reuse, require matching cumulative overlap and preserve RingCT activation semantics. Never cache/replay output or ring requests, skip distribution history, choose an alternate node/route, or expose node/recipient/transaction details in diagnostics. Preparation progress must not acquire the engine mutex; a new preparation must stop on lock/background cancellation, with only completed count parts retained.

- Preserve named wallet IDs, legacy vault paths and wallet-specific network consent. New setup is Mainnet software creation, supported seed import or Keystone. Never overwrite an older wallet while simplifying navigation.
- PIN, biometric and duress changes must preserve authenticated encryption, migration recovery and per-use strong biometric CryptoObject enforcement. Security commits must be fenced against lock; never migrate an active setup lease. Duress is explicitly opt-in, acts only on this app/profile, and must never be exercised against real user data. External backups and blockchain records remain outside its scope.
